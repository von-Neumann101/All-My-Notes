## Workflow
Workflow本身可能会比较简单，但是容易出现非常多的“边缘情况”，一个酒馆的Workflow可能因为顾客点了蛋糕而出现Runtime Error，我们不总是能涵盖所有Workflow，这很难，而且可能会使得Workflow变得极其繁杂——解决方法就是Pi-Runtime
## Pi-Runtime
用一个Workflow涵盖所有的Workflow
![[Pasted image 20260525164127.png]]
假设我们现在有两个用户：a和b，他们都想调用deepseek模型。a要查阅图书，b要查阅旅游攻略
1. Initialization：两个绑定
第一步：由于两个用户账号不一样，先根据user_id绑定模型
第二步：寻找之前的log——长期记忆和当前任务的对话
2. Assembly：组装生成prompt
根据两个用户不同的Query，找相关的SKILL.md（工作指南）和对话的log，再加上一些系统提示词（比如：请不要弄虚作假，请文明用语）
3. Invocation：调用ai
将提示词输入，得到了[[04#^f0aa01|大模型输出的三个部分]]，此处还有判断调用哪个模型
4. Execution：执行tool call
运行本地工具
5. Memory and Output：保存记忆和输出
输出包含tool call的结果和一般的输出，同时把结果写入session log中
>Pi-runtime 不是依靠一个独立后台线程硬编码地永久循环运行，Pi 内部确实有硬编码的 agent-loop 框架，但每一轮调用什么工具、需要循环多少次、何时正常结束，主要由模型输出及 runtime 的中止/跟进机制动态决定。
## Event, Hooks, Monitoring
![[Pasted image 20260529143952.png]]
循环中会包含[[未知补全#Hooks|hook（钩子）]]，比如我要写log，模型会判断要简略还是详细——如果简略就打开少量钩子，反之则打开所有钩子释放所有的event（每个event都会在log里加入东西）
我们还可以写入event handler（句柄处理器），当符合某个条件的时候，跳出循环
