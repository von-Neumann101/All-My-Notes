# Matrix
![[Pasted image 20260504150846.png|338]]

Openclaw中的通讯方法有两种——[[未知补全#HTTP|HTTP]]（有问必答，不问不答），[[未知补全#WebScoket|WebScoket]]（双向双工）
HTTP不适合在发送消息（微信不是一问一答，问和答不是绑定的），且不适合于双工（对讲机和视频会议的区别）

**Matrix**——私域即时通讯（加密微信），且可以连接人和机

![[Pasted image 20260504151625.png]]
传统方式是A（用户），发送到B（服务器），再由服务器分发给对应用户
而Matrix是用户直接直接连接，自动组织网络（中心节点丢失整个网络不受影响——每个个体都是一个”中心“）

群聊：
Matrix中，一个用户（或者说一个账号）称为一个HomeServer。如果ABC三人想要创建一个群聊，需要创建一个Room
每一条消息会多份复制，比如A发送了一个消息，所有的群成员都会保存这个信息
每个参与房间的 homeserver，会保存它接收到并允许保存的事件历史。
![[Pasted image 20260504155049.png]]

Event：活动，每次发送信息或者进行了任何行为称之为事件
通过[[未知补全#MEG|MEG]]（一种DAG——有向无环图）来保存每个event的时间（梳理时间）
![[Pasted image 20260506092144.png|441]]

每个homesever都需要配置一个数据库，其数据需要被长期保存，而其路由是一直在变化的（Matrix的特性导致）

![[Pasted image 20260515103819.png|562]]
无论是聊天消息、WebRTC 通话建立、IoT 传感器数据、正在输入提示，本质上都被**包装成 JSON event，然后同步进 MEG/DAG**。
Matrix 负责：event 的存储、签名、同步、联邦一致性。
应用负责：解释 JSON payload 的含义。
![[Pasted image 20260515104039.png|511]]
Matrix只负责保存JSON，维护MEG，JSON的解释完全由用到JSON的应用来解决

![[Pasted image 20260506093013.png|615]]

1. 网络的物理和逻辑拓扑——哪些homesever？如何连接？identity怎么对应用户？
2. API

# Channel
![[Pasted image 20260506093629.png|325]]
**握手**：我平时在北京，但是我到南京了，上海人给我打电话，握手的过程就是——上海到北京，北京到南京，南京到上海，这样我们直接南京和上海连起来

OpenClaw 本身可能有自己的核心系统/API/消息处理逻辑。但为了接入微信、钉钉这类外部平台，需要在外面再加一层适配层。
```
微信 / 钉钉 / Web / App
        ↓
    Channel 适配层
        ↓
    OpenCloud 核心系统
```

**GateWay**
Gateway用于转发和调度——由于Openclaw要同时支持很多东西，显然不能让每个组件之间通信连接，Gateway 的作用是把它们统一接到一个中心，这样所有组件只需要懂一套 Gateway 协议，系统更容易扩展。

**OpenClaw-node**
> node 是一个 companion device，例如 macOS、iOS、Android 或 headless 设备，它连接到 Gateway WebSocket，并以 `role: "node"` 暴露一组可被调用的命令表面，例如 `canvas.*`、`camera.*`、`device.*`、`notifications.*`、`system.*` 等
```
1. 和 OpenClaw Gateway 建立 WebSocket 连接
2. 注册自己是一个 node
3. 把自定义应用/设备的能力暴露给 Gateway
4. 接收 Gateway 的调用请求
5. 把结果再通过 WebSocket 返回 Gateway
```
我们不能让Gateway知道如何调用所有的软件和功能，但是我们能把功能抽象，然后接入Gateway
```
Telegram / Slack 这种内置渠道：
    直接接入 OpenClaw Gateway
    不需要 openclaw-node

自定义 Web App：
    需要通过 openclaw-node
    再接入 OpenClaw Gateway
```
openclaw-node在连接Gateway以后，会告诉Gateway其能力，同时Gateway会维护一张表，用于存储每个能力对应的node

总结一下：
```
openclaw-node = 把外部软件/设备/本地能力包装成 Gateway 能识别和调用的 node capabilities  
Gateway = 维护这些 node 的连接、能力表、权限和调用路由
```
**Channel**
将Openclaw接入微信，Channel可以把信息标准化。
比如，微信所暴露的API会给出这样的信息：
```JSON
{
  "from_user": "wxid_123",
  "chatroom": "group_456",
  "msg_type": "text",
  "content": "帮我看一下今天机械臂实验日志",
  "timestamp": 1234567890
}
```
Channel将这个消息变为OpenclawAPI所接受的形式：
```JSON
{
  "channel": "wechat",
  "conversation_id": "wechat:group_456",
  "sender_id": "wxid_123",
  "message_type": "text",
  "text": "帮我看一下今天机械臂实验日志",
  "timestamp": 1234567890
}
```
否则，Agent将不知道：
- 这条消息从哪里来？  
- 是谁发的？  
- 属于哪个会话？  
- 应该发给哪个 Agent？  
- 回复发回哪里？
