## Non-blocking I/O
![[Pasted image 20260520200709.png]]
是让 Gateway 不因等待外部 I/O 而阻塞主线程；等待期间可以继续调度其他事件，从而提高并发能力、响应性和资源利用率。
比如说我有一个http请求，同时又有一个调用画图工具的任务，如果http超时，我不会等着他，而是等待的时候顺便调用画图工具

![[Pasted image 20260520201539.png]]

## Single Thread Main Loop
![[Pasted image 20260520205058.png]]
Node.js 的**事件循环**主线程，反复检查有没有事件需要处理
```
while (Gateway 没有退出) {
    1. 检查事件队列里有没有事件
    2. 取出一个事件
    3. 执行这个事件对应的 handler
    4. 如果 handler 发起异步 I/O，就登记回调，然后立刻返回
    5. 继续处理下一个事件
    6. 某个 I/O 完成后，把结果重新放回事件队列
}
```
Main Loop 是一个很轻的事件处理循环，他不具体解决任务，而是把大任务派发给别的地方做。不过它会执行一些**轻量逻辑**

**登记回调**
读文件->打印->干其他事的同步写法
```
const data = readFileSync("config.json");
console.log(data);
console.log("继续处理别的事");
```
异步写法就是
```
fs.readFile("config.json", "utf8", (err, data) => {
  console.log("文件内容：", data);
});
console.log("先做别的事情");
```
Main Loop的主线程不会被阻滞，有些IO请求被交给系统处理
## Worker Thread Pool
![[Pasted image 20260521092546.png]]
承接上面的Main Loop，Pool处理的是重型任务(主循环只指挥，重活交给线程池做)
Worker Thread Pool 在其他线程里处理，处理完以后，通过 Promise callback 把结果交回 Main Loop
```
轻任务：
Main Loop 自己处理
例如：判断事件类型、路由、登记回调、更新状态

重任务：
丢给 Worker Thread Pool
例如：压缩、加密、复杂计算、同步文件操作、CPU 密集处理
```

## Gateway Redundancy
![[Pasted image 20260522150736.png]]
- **Standby Mode**
Backup Nodes平时处于时刻准备的状态，但平时不工作。当主Gateway失败的时候，流量被切换到Backup Nodes
```
Gateway 还活着：
通过禁用异常组件、修改配置、断开坏 Node、清理 session 等方式在线修复。
Gateway 已经卡死/崩溃：
无法在线修复，只能依靠 Standby Mode 接管流量，然后重启或重新部署主 Gateway。
```
- **Shunting Mode**
实时负载均衡，把请求分流到多个活跃服务器
-  **Decomposition Mode**
把“一个复杂任务”拆成多个子任务，解决单个任务太重

![[Pasted image 20260522153654.png]]

## Delicated Process Offloading
![[Pasted image 20260522155452.png]]
> [!NOTE] Delicated
> 之所以要把本地服务或者Web服务和Gateway解耦，是因为要保证Gateway**任务调度**而非任务执行的抽象
### Systemed Implement
```ISOLATION
1. 进程隔离
本地模块崩溃，不直接导致 Gateway 崩溃。
2. 内存隔离
模块不能直接读写 Gateway Core 的内存状态。
3. 权限隔离
模块可以用更低权限运行，不给它完整 Gateway 权限。
4. 生命周期隔离
模块可以单独启动、停止、重启。
5. 资源隔离
可以限制它的 CPU、内存、文件访问、运行时间。
6. 错误隔离
模块报错、超时、卡死，只影响该模块，不拖死 Gateway。
```
### Web Server Deployment
把高外部流量放到专用 Web Server 上处理，再通过专用链路和 Gateway 通信，目的是把外部高吞吐流量与 Gateway 内部逻辑分离。
```
外部大量请求 / 文件 / 流式数据
↓
Web Server Deployment
先接住、过滤、缓存、预处理、限流、鉴权、聚合
↓
只把“需要 Gateway 决策的事件/摘要/结果”交给 Gateway Core
```
## MCP
[[未知补全#MCP(Model Context Protocol)|MCP]] 是 AI / Gateway 与**外部工具、外部数据**源之间的标准化转接口。
在Openclaw内部的workflow如下：
```
LLM 产生工具调用意图
↓
Gateway / Agent Runtime 判断、校验、路由
↓
通过 MCP 调用外部工具
↓
MCP Server 返回结果
↓
Gateway 再交给模型或用户
```
## Docker
![[Pasted image 20260522163123.png]]
把高风险工具/MCP Server 放进 Docker 容器里运行，并用一组隔离策略保证它坏了也不拖垮宿主系统和 Gateway
```
用户请求
↓
Gateway 判断需要调用某个外部工具 / MCP Server
↓
Gateway 不在自身进程里执行这个工具
↓
启动或连接一个 Docker 容器
↓
工具在容器内部运行
↓
结果通过 stdio / HTTP / MCP 协议返回 Gateway
↓
容器可被销毁、重启或复用
```
## The Distributed Mesh Topology
既然任务可以被拆分、卸载、隔离，那这些执行单元**就没必要都在同一台机器上**
![[Pasted image 20260522163651.png]]
- Tailscale
把不同地区、不同网络里的节点，通过加密 VPN 连成一个统一逻辑网络
例如：
```
你在新加坡的电脑
家里的 Windows 主机
实验室的机械臂电脑
云服务器
另一台跑模型的 GPU 机器
```
它们本来可能在不同局域网、不同公网环境、甚至没有公网 IP。用了 Tailscale 以后，它们可以像在同一个私有局域网里一样互相访问。
- Bonjour / mDNS
在同一个局域网里自动发现设备，让硬件或节点能自动找到 Gateway
普通情况下，要先知道设备IP，然后再配置Gateway去连接
但是使用握手以后，设备在局域网内广播“我这里有一个可连接的服务”，而这个服务可能对应 OpenClaw 里的 Node、Channel、Gateway 或某个硬件 Bridge
